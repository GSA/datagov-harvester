Findings & recommendation

User-visible slowness during rebuilding: 37% of searches took over 5s and 29% took over 10s, against 5% and 5% at baseline. p75 moved from 1.23s to 10.93s.

Read the tail, not the median: p50 barely moves while the p75 and the over-10s share move a great deal. That is what a user experiences as broken rather than slow.

The cluster's own query time rose from 53ms to 148ms median (266ms to 1042ms p95) — real degradation, but measured in milliseconds.

End-to-end HTTP p95 for the same window was 21.9s, roughly 21× the cluster's own p95. So most of the wait was not spent executing the query. It sits above OpenSearch — catalog page render, the request path, or the monitoring host’s own network. Capacity work on the cluster would not address it.

The cluster was never saturated: search queue peaked at 0 with 0 rejections.

Peak heap 74% (vs 73% at baseline), CPU p50 8% (vs 6%), young-GC 0.14% of wall clock. Peak indexing 162 docs/s. Adding nodes would not have changed the end-to-end numbers above.

Availability held: 444/445 checks passed and the dataset count never dropped below 547,909.

No search returned zero results and the alias switch was atomic, so readers were served the old index for the entire rebuild. The zero-downtime property held.

Recommendation

Run rebuilds off-peak. 29% of searches over 10s is a poor experience however the time is spent, and the run takes about an hour — off-peak costs nothing.

But do not justify it as cluster health. The cluster had ample headroom; that framing would send capacity work in the wrong direction. If rebuilds must run during peak, investigate the catalog request path, not OpenSearch sizing.

Caveats on these numbers. The baseline phase has only 64 clean samples — a thin basis for a tail estimate; 15+ minutes is better. Latency is measured from a laptop over the public internet and includes full page render, so it is a user-experience proxy, not a cluster metric — the millisecond figures above are the trustworthy server-side view. Samples overlapping a cf ssh cluster sample are excluded from all latency figures. To locate the missing seconds, a future run should capture catalog app response times alongside these.
