# Monitoring the catalog during an OpenSearch index rebuild

How to verify that Catalog keeps serving search while an OpenSearch rebuild runs,
and to capture chart-ready data on what the rebuild costs the cluster.

The point of the zero-downtime rebuild is that reads keep being served from the
old index until the alias swap. This tooling is how you *prove* that, rather than
asserting it.

## Scripts

| Script | Role |
|---|---|
| `scripts/monitor_catalog_stage.py` | Samples the catalog and the cluster; writes CSV |
| `scripts/opensearch_metrics_json.py` | Cluster-metrics payload streamed into the CF app; emits one JSON object |
| `scripts/monitor_report.py` | Renders the CSVs into a self-contained HTML report with charts |

`opensearch_metrics_json.py` is the machine-readable sibling of
`scripts/opensearch_status.py` and reaches OpenSearch the same way
`scripts/opensearch_status.sh` does: `cf ssh` into a running app instance, which
is inside the VPC that can see the cluster.

## Prerequisites

- `cf` CLI logged in (`cf login --sso`) and targeting the right space:
  `cf target -o gsa-datagov -s staging`
- Python 3 only — the scripts use the standard library, no install step.
- Basic-auth credentials for the environment, if it enforces them, via
  `CATALOG_USER` / `CATALOG_PASS`. As of 2026-07-28 staging returns 200 without
  credentials, but the script sends them regardless so it keeps working if auth
  is re-enabled.

## Procedure

### 1. Verify the tooling before you rely on it

`--once` runs a single sample of each check and exits. Do this first — a broken
check that silently reports PASS is worse than no monitoring.

```bash
python3 scripts/monitor_catalog_stage.py --once
```

Expect three PASS lines (DASHBOARD, SEARCH, OPENSEARCH). If OPENSEARCH fails,
`cf` is not logged in or is targeting the wrong space.

### 2. Capture a baseline before touching anything

```bash
RUN=monitor-runs/$(date +%Y%m%dT%H%M%S)
python3 -u scripts/monitor_catalog_stage.py --outdir "$RUN" --phase baseline
```

Leave it for **at least 15 minutes**. At a 10s search interval that is ~90
samples, enough for a p95 to mean something; at 5 minutes it does not. Run it in
one terminal and watch it, or background it and `tail -f "$RUN/monitor.log"`.

### 3. Mark the phase, then start the rebuild

The monitor re-reads `phase.txt` on every sample, so you label the timeline
without restarting anything. Write the label **immediately before** triggering
the rebuild — baseline samples mislabeled as `rebuilding` are harmless, but
rebuild samples labeled `baseline` corrupt the comparison.

```bash
echo rebuilding > "$RUN/phase.txt"
# now run Actions -> Rebuild OpenSearch Index
```

When it finishes (or fails):

```bash
echo post-rebuild > "$RUN/phase.txt"
```

Keep sampling for 10+ minutes afterward. The `post-rebuild` phase is what shows
recovery — that latency and heap came back down instead of staying elevated.

### 4. Stop and report

```bash
kill -INT <pid>        # Ctrl-C if in the foreground; closes CSVs cleanly
python3 scripts/monitor_catalog_stage.py --report "$RUN"      # per-phase stats
python3 scripts/monitor_report.py "$RUN" && open "$RUN/report.html"
```

Data is flushed per row, so even a hard kill loses nothing.

If you background the monitor, note that `kill -INT` on the wrapping shell does
not stop the Python process — target the `python3 ... monitor_catalog_stage.py`
PID directly (`pgrep -f monitor_catalog_stage.py`).

## What gets sampled

| Check | Default interval | Assertion |
|---|---|---|
| SEARCH | 10s | `GET /?q=school OR zz<24 random chars>` returns a non-zero hit count |
| DASHBOARD | 30s | homepage total count is >= `--min-count` (default 547,883) |
| OPENSEARCH | 60s | cluster reachable; records CPU, load, RAM, heap, GC, thread pools, indexing/search rates, shard counts, alias targets |

The random suffix on each search defeats any query cache, so every sample
measures real work. The `OR` keeps the query cheap to satisfy while still
exercising the search path.

Two things about the search assertion: hits cap at `Found over 10000`, so the
**search count will not move even if the index shrinks** — the dashboard count is
the completeness signal and search is the availability signal. And a query whose
matching term finds nothing is reported as `zero results`, which is a FAIL.

## Output

```
monitor-runs/<timestamp>/
  checks.csv              one row per HTTP check (long format: dashboard + search)
  opensearch_cluster.csv  one row per cluster sample
  opensearch_nodes.csv    one row per node per sample
  raw/os-<epoch>.json     full JSON snapshot per sample
  monitor.log             the running log, same as stdout
  phase.txt               current phase label (you write this)
  report.html             generated by monitor_report.py
```

Every row carries `phase`, so the report shades the rebuild window and
`--report` breaks every statistic out per phase.

## The `os_sample_inflight` column — read this before analyzing latency

`cf ssh` is a heavyweight local subprocess and it contends with the HTTP checks
**on the monitoring host**. Measured directly on 2026-07-28: searches at ~1s
baseline spiked to 11.8s while a sample was in flight, and one run logged a
31.98s search that was purely local contention.

Checks that overlapped a `cf ssh` sample are tagged `os_sample_inflight=1`. Both
`--report` and `monitor_report.py` exclude those rows from latency statistics and
charts, while still counting them for availability. **If you analyze the CSVs by
hand, apply the same filter** or your p95 will describe your laptop rather than
staging.

To eliminate the interference entirely, split it across two processes:

```bash
# terminal 1 -- HTTP timing only, no cf ssh
python3 -u scripts/monitor_catalog_stage.py --outdir "$RUN-http" --no-opensearch

# terminal 2 -- cluster metrics only
python3 -u scripts/monitor_catalog_stage.py --outdir "$RUN-os" \
  --search-interval 99999 --dashboard-interval 99999
```

## Useful options

```
--url URL                  target environment (default staging)
--min-count N              dashboard threshold (default 547,883)
--term WORD                matching half of the OR query (default "school")
--search-interval S        default 10
--dashboard-interval S     default 30
--opensearch-interval S    default 60
--no-opensearch            skip cf ssh sampling entirely
--no-raw                   do not keep raw JSON snapshots
--cf-app / --cf-instance   default datagov-harvest / 0
--once                     one sample of each, then exit
--report DIR               summarize an existing run and exit
```

For another environment, point `--url` at it and pass the matching app and count,
e.g. `--url https://catalog-dev.data.gov/ --cf-app datagov-harvest --min-count 1`.

## Stored baselines

None committed yet. When you capture a baseline worth keeping, copy the three
CSVs into `docs/ops/baselines/<env>-<date>/` with a README recording the window,
the numbers, and the index topology at capture time. `monitor-runs/` itself is
gitignored, so a run there is working data only.

A baseline is what makes the next rebuild interpretable: staging search has a
heavy tail even at idle, so without one there is no way to tell a rebuild-induced
slowdown from normal behavior.
