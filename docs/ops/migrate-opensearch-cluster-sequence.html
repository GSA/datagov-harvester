Migrate OpenSearch Cluster — the happy path

One workflow_dispatch of .github/workflows/migrate_opensearch_cluster.yml with default inputs. Nothing the live cluster serves is touched until stage 6, so every failure before that point is free. Generated from the workflow and the bin/ scripts it calls.

  • live cluster untouched
  • verification gate — aborts the run
  • traffic moves / irreversible

Why the ordering is what it is

Failure before stage 6 costs nothing

The live cluster receives no rebuild traffic at all. On a build failure the replacement is deleted and the live cluster is exactly as it was — or pass on_build_failure: keep to retain it and resume with start_at: rebuild.

The rename is what moves catalog

datagov-catalog's .profile resolves ${APP_NAME}-opensearch and never reads OPENSEARCH_SERVICE_NAME, so cf set-env on catalog is a silent no-op. Step 6c is the only lever — and needs no catalog-side change.

Steps 6a→6b are adjacent on purpose

Two instances cannot share a name, so the canonical name must be absent for at least one command. Running instances are unaffected (VCAP_SERVICES is read at container start); only a new start in that gap would fail. Restart crons queue on the shared concurrency group rather than racing it.

Neither app is repointed

Both resolve the canonical name, so the cluster moves underneath it. An earlier version pinned the harvester to …-next before the renames and cleared it after — the two cancelled out, and in between the variable named an instance the rename had just removed.

Both gates need the flag

compare alone prints its counts and exits 0, so --fail-on-discrepancy is what makes it a gate rather than a log line.

Deletion is last, and its own job

The replaced cluster is the rollback path, so it outlives every verification. delete-service --wait blocks on AWS teardown (>10 min for an es-medium), so a slow cleanup must not be reported as a failed migration.

Other paths

InputWhat changes
stop_after: verify Stops after stage 5 with the cluster built, bound, verified and parked; both apps stay on OLD. Deploy code, then re-dispatch start_at: cutover. For schema-breaking changes — both apps must move together, so the split is before stage 6, not inside it.
start_at: rebuild / cutover Skips earlier stages. Every stage is idempotent and detects work already done, so this is an optimisation, not a correctness crutch — it exists so a prod es-large provision is not repeated.
keep_old_cluster: true Promotes but skips stage 8, leaving the replaced cluster for a soak.
next_plan Resize. The broker cannot change an instance's plan, so a new instance is the only way.
promote fails midway Nothing is deleted: renames may be half-applied, so the run stops for a human. bin/report_opensearch_cluster.sh shows where each app landed.
